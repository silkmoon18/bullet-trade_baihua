## 验证和交付

代码已经完成，helper保持可独立导入的单文件及Python 3.8语法；`.pyi`同步新公共门面。普通GoodETF仍默认09:30决策、09:30执行，调仓不启用独立变体的清仓确认机制。盘前候选仅包含代码/名称，不提前计算价格、权重或订单。服务器候选订阅失败不影响已完成的账户对账，也不会虚报订阅成功。候选批次超出行情订阅上限时，恢复到已有持仓的订阅；持仓预热也失败则移除本策略的预热所有者，避免失败的候选集合占用随后执行行情的订阅额度。清理请求失败时保留清理跟踪，不影响其他策略所有者。

日志与通知移出普通GoodETF的提交路径：成功决策日志随当天冻结快照保存，执行完接口调用后输出；QMT计划卡片所需的补充快照读取也移到JQ提交之后。原生JQ调用顺序、撤单、资金不足裁剪、未成交和部分成交处理保持原样，不补单。QMT仍先提交，双账户资金独立；原有券商新快照与行情时效校验未跳过。

资金口径沿用之前已用于延迟实验的冻结规则：JQ采用选股时总资产，QMT采用服务器提交时总资产。它与远端未冻结的JQ入口在清理持仓后读取资产的口径存在区别，卖出费用可导致目标金额差异。对比提速前后回测时应使用同一冻结版本；本次不把之前实验的变化归为延迟优化业绩。

`g.bt_last_rebalance_timing`与聚宽`调仓耗时`日志提供：

| 字段 | 口径 |
|---|---|
| `decision_ms` | 冻结决策回调的处理耗时 |
| `first_jq_order_ms` | 本轮执行开始至第一次尝试JQ下单接口 |
| `qmt_submit_ms` / `qmt_accepted_ms` | 本轮执行开始至QMT目标请求调用/收到接受响应，均不是成交时间 |
| `orders_ms` | 全部账户的提交阶段耗时 |
| `notification_ms` / `logs_ms` | 提交后通知/输出日志的耗时 |
| `total_ms` | 本轮执行、通知和日志输出的合计，不含刻意配置的选股与下单间隔 |
| `rpc_connections` / `rpc_reused` | 本轮执行期间新建连接/获取复用连接的次数 |
