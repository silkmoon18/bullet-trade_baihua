## 09:26选股、09:30跌停价卖出实验（仅JQ）

[`good_etf_0926_limitup.py`](good_etf_0926_limitup.py)沿用历史文件名，**已取消涨停价买入**。该独立回测策略不覆盖原GoodETF或清仓后买入变体。09:20读取前一交易日ETF池、成交额与单位净值；09:26用当日开盘价计算折价，选择折价最深的前三只，按绝对折价比例分配95%目标权重，并冻结当日决策，不下单。开盘价及涨停过滤所需行情的有效性、港股/流动性过滤、净值日期、排序和权重公式不变。

按用户最新指示（2026-10-14），不使用涨停价买入或限价资金等待队列，执行改为：

- 09:26只冻结选股、权重、开盘参考价及JQ资金基数，调用现有`prepare_rebalance`，不提交任何委托。
- 09:30先以当天跌停价调用`order_target`卖出计划外持仓及入选标的的超额部分；保留仍需持有的部分，不每天全清仓。减仓数量按当前持仓市价和整手算差额，跌停报价不参与目标份额换算。
- **本轮跌停价卖单全部成交后才买入**：helper以记录的委托ID读取`get_orders()`，逐笔确认实际成交数量足够，再确认本轮卖单不在`get_open_orders()`中及对应持仓已更新到目标。仅持仓减少、委托消失或手动卖出，不能冒充本轮成交。
- 若09:30同步完成卖出，就继续买入；否则通过`every_bar`每分钟继续只读确认。全部完成后以冻结资金基数和权重调用原生`order_target_value`市价买入一次，不传买入限价。已完成减仓的入选标的不重复调仓，仍应保留的持仓不清空。
- 卖单部分成交则等待；未足量成交即终结（含撤单、拒单或被平台缩量）、未接受或提交未知则本轮不买入，不盲目重发。回报暂不可查时等待查询恢复；不会把资金或持仓变化当作券商成交。
- 重启从`g`恢复当日卖出确认状态及冻结决策，不重新选股、不重复卖出或买入，旧日计划不在次日继续买入。等待期间触发既有止盈/止损的标的不再被冻结计划买回。
- **不补买、不追单**：市场价变化或买入阶段现金不足时，聚宽仍可能缩量、部分成交或拒单；这些买单不会按分钟继续补足。既有风控时间和阈值、平台费用不变。

### 仅回测买入涨价压力测试（2026-10-15）

顶部新增`BUY_PRICE_INCREASE = 0.005`：只在该独立策略的历史回测买入时，给原模型成交价额外增加0.5%；`0.001`为0.1%，`0`完全沿用原执行路径，不增加行情查询或滑点切换。模拟交易忽略此参数，不传到QMT，不影响默认GoodETF。

原模型为聚宽原生市价撮合价加0.001元（共享`FixedSlippage(0.002)`的一半）。实验目标模型价为`(撮合参考价 + 0.001) × (1 + BUY_PRICE_INCREASE)`，不是提高买入限价，也不是额外扣手续费。例如原模型买入价1.001元，参数0.005时模型价1.006005元。helper在09:30使用当日开盘价，若卖单直到后续分钟才全部成交，则使用**实际买入时的最新价**，不沿用09:26冻结参考价。

每笔市价买单提交前由helper临时设置相应固定滑点，原生同步撮合后在`finally`中恢复原固定滑点，卖出调仓及止盈止损仍用原设置；冻结计划保存比例以支持等待卖出期间重启。选股、排序、权重公式和目标资金基数不改，但更高买入成本可能改变整手数量、持仓成本、后续风控触发和回测收益。资金/成交量/涨跌停仍由平台处理，不能保证每笔成交；货币基金等平台不支持滑点的品种不强行改价。日志`回测买入涨价`区分原模型价、额外比例及目标模型价，真实成交以聚宽交易记录为准。[聚宽滑点文档](https://cdn.joinquant.com/help/img/JoinQuantAPI.pdf)说明固定价差买卖各承担一半。本地测试验证参数、设置/恢复和隔离，最终需在聚宽重新运行分钟回测核对实际成交。

跌停价只是卖出最低限价，不表示实际会按跌停价成交，也不保证卖出一定完成。该流程通过`execute_prepared_rebalance(..., jq_wait_for_sells=True)`转交现有通用分阶段接口，并使用`prepare_sell_then_buy(..., liquidate_all=False)`保留入选持仓。原有全清仓变体的默认行为不变，默认GoodETF仍保持原生一次性调用方式，QMT执行链路不变。阶段状态、查询和确认全部位于helper，策略文件仅声明决策和调用薄入口。

使用**分钟回测**，资金在聚宽回测界面填写。策略不声明ID、不读取`jq_runtime_config.py`、不做远程预检或向QMT发送目标。**手动更新两份文件**：完整替换本策略，并将当前`helpers/bullet_trade_jq_remote_helper.py`上传至聚宽研究根目录，即使原文件已显示API25也必须更新（本次为兼容原接口的新增可选参数）。私有配置、默认GoodETF、服务器及QMT bridge不用更新。校验命令为`python -X utf8 scripts/export_joinquant.py --strategy good_etf_0926_limitup --validate-only`。本地契约测试不等同于聚宽历史撮合回测，收益需在平台重新验证。

## 当前使用限制

`good_etf.py`已经不再保存host、token、profile、Webhook或账户开关，也不再包含TCP、QMT回调、意图恢复、模式解析、通知异常处理、账户下单分支、下单类型实现、平台参数设置或调度注册。策略文件只保留最薄的聚宽入口和运行时安装声明，以及ETF选股、目标权重、止盈止损阈值等决策代码。`JoinQuantRuntime`按配置分别驱动JQ和QMT账户；每个账户的目标金额均按其自己的`组合总资产 × DEPLOY_RATIO × 归一化权重`计算。详细边界以仓库根目录[`AGENTS.md`](../../AGENTS.md)为准。

当前账户组合的边界是：

- `BACKTEST`：始终使用聚宽原生回测接口；helper必须与策略一起上传，关闭远程预检时不读取私有profile；
- 仅JQ：正常调用聚宽原生下单、撤单和模拟撮合，不叠加QMT的0.2%价格边界，由聚宽维护资金、持仓和指标；维持现有JQ目标买入计划通知；
- 仅QMT：使用StrategyLedger真实组合与目标接口并阻断聚宽原生交易函数；
- JQ+QMT：同一组选股权重分别按两个账户自己的资金和持仓执行，止盈止损也分别使用各自成本；QMT开启时只发送QMT计划、订单和成交通知，不再重复发送JQ计划卡片。

QMT调仓先以沪深市价IOC卖出，收到终态回报后再按0.2%条件限价买入；买入阶段各标的独立等待和成交，不会因另一标的部分成交而全部阻塞。未完成的当日目标由常驻服务器在次日00:00主动撤单并闭环。止损使用市价IOC，止盈继续使用0.2%条件限价。服务端交易总开关仍独立控制是否实际下QMT订单。

helper在09:20触发QMT盘前账户对账，提前恢复旧目标、预订阅候选及已有持仓行情。实际选股/发单时间以策略顶部参数为准：原GoodETF为09:30；开盘价变体为09:26清仓、09:30起买入。服务器提交时取得新券商快照；首笔发单在2秒内且没有新的账户事件或对账时复用它，否则重查，后续每笔仍重新核对。BigQMT查询同批交给bridge；只有QMT买入使用参考价上浮0.2%的固定限价。

开盘价变体经用户明确授权，使用helper的通用`prepare_sell_then_buy`/`advance_sell_then_buy`：清空全部旧归属持仓（含再次入选的标的），两个账户各自确认清仓后才买入。JQ买入仍是原生市价单、仅提交一次，没有分钟买入补单；QMT的订单状态和余量继续由服务器管理。若09:30未卖完，后续分钟继续确认，不提前买；重启恢复不重新选股，旧日计划不继续买入。详情见[执行指南](../../docs/live-ledger/07-status-and-usage.md#开盘价选股0926清仓--0930起买入变体)。

当前仓库代码具备回测、JQ模拟、QMT远程和JQ+QMT并行链路。真实资金启用前仍必须在目标QMT环境完成模拟与小额人工验收，并由用户明确放行。

## 旧模拟交易的调度恢复（API25）

旧模拟交易可能保存直接调用`market_open`的09:30任务；新版该函数只生成权重和参考价，真正执行由helper入口负责。只更新函数源码或重建RPC运行时，不会把旧日程迁移为新入口；因此可能选出标的却没有提交目标。本地已复现该兼容缺口，不能以此代替聚宽侧实际日程和成交验收。

三份策略各自用薄函数`_declare_schedule`声明自己的日程，首次`initialize`及每次`process_initialize`均调用它。helper的`schedule_daily(..., replace_existing=True)`先校验开盘配置和回调，再通过`unschedule_all`清理当前策略的全部定时任务并重新注册；若本策略还有自定义日程，也必须纳入这一声明。平台每次注册都会新增任务，不能在旧任务上直接追加。重复恢复只保留一组日程，正常的09:26独立清仓变体和反转周期不变。

恢复不调用`initialize`，不清`g`中的候选/信号/冻结决策，不清JQ资金、持仓或QMT账本；注册不执行回调、不补当日错过的09:30目标，也不新增JQ买入补单。日程中的helper回调仍是可序列化的顶层函数；运行时恢复后引用当前策略的决策入口。

手动更新清单：暂停相关聚宽模拟交易，上传`helpers/bullet_trade_jq_remote_helper.py`至研究根目录，完整替换正在使用的策略源码，再启动同一模拟交易。共享helper的`good_etf_open_0925.py`、`etf_reversal.py`如也在运行，必须一起更新。`.pyi`仅用于本地IDE，不上传；私有配置、服务器和QMT bridge无需变更。不要只手改期望API版本。

验收日志应显示`helper API=25`、`任务调度完成`，以及普通GoodETF的`调度入口 | 时间=09:30 回调=_decide_joinquant_open_rebalance`。随后在正常执行时间核对冻结目标、JQ调用及服务器QMT目标；未到时间时不能把恢复日志当作已成交证据。

## 下单链路提速（当前helper API25）

盘前helper保存候选代码及名称，QMT服务器预订阅候选与已有持仓的行情。选股/下单回调前一分钟预热RPC连接，默认09:29；独立09:26变体则在09:25、09:29预热。正常请求复用同一经过认证的连接，空闲超过90秒、身份变化或异常后丢弃连接；可能已发送的写请求不自动重发。预热只准备连接和行情订阅，执行时仍按原规则取得新券商快照并检查行情时效。

普通GoodETF的成功决策日志缓存在helper中，所有已启用账户的委托接口调用完成后才发送计划通知和输出日志。JQ仍按原生接口调用顺序执行。冻结权重、参考价、JQ资金基数及QMT价格边界沿用已有延迟实验语义。独立清仓买入变体保留其明确授权的阶段流程。

日志`调仓耗时`及`g.bt_last_rebalance_timing`包含决策耗时、执行开始至首个JQ接口调用/QMT目标提交与接受的耗时，以及通知、日志和连接次数。JQ接口调用与QMT接受目标均不代表已成交，实际服务器发单需对照原有执行日志。先保持两个时间均为09:30对比性能，再仅改下单时间做延迟实验；代码提速的收益影响尚未取得聚宽/QMT实测。

使用时同时更新策略与研究根目录helper（API25）；候选行情预订阅还需服务器的`strategy.prepare_session`实现。链路优化代码已部署到当前fork服务器，2026-10-08服务及QMT链路复核READY；可选ID及调度恢复仅修改聚宽侧代码，不要求再更新服务器或重建账本。聚宽侧上传及实际执行需单独验收。设计及验证记录见[GoodETF下单链路提速](../../docs/live-ledger/45-goodetf-latency.md)。

## 选股与下单时间实验（当前helper API25）

策略顶部独立配置两个时间，默认均为`09:30`。同一时间由helper在一次回调内先选股、再下单，避免依赖同分钟回调的注册顺序。

```python
OPEN_DECISION_TIME = '09:30'  # 计算折价、过滤、排序和权重
OPEN_ORDER_TIME = '09:35'     # 使用冻结结果下单，实验5分钟延迟
```

测试0、1、5、15分钟延迟时，保持`OPEN_DECISION_TIME='09:30'`，仅将`OPEN_ORDER_TIME`分别设为`09:30`、`09:31`、`09:35`、`09:45`。两个时间都必须是盘中`HH:MM`，下单不能早于选股；配置错误在注册调度前报错。请使用分钟回测，并保持回测区间、资金、成本和其他参数相同。手续费、整手、资金不足及T+1等仍由JQ原生撮合决定。

选股回调只返回目标权重与参考价。helper保存当天决策；下单时不重新获取选股价格、不重新过滤、排序或计算权重。JQ目标金额按**选股时的JQ总资产 × 冻结权重**确定；实际成交使用下单时的JQ原生价格和撮合规则，不把参考价作为JQ限价。空目标在下单时清理持仓；数据缺失或选股失败则跳过，不把失败当作清仓。当天快照可随`g`恢复，跨日快照拒绝执行；下单回调只提交一次，不增加分钟补单或先卖完再买机制。

该配置也影响聚宽脚本驱动的QMT目标提交时间：QMT继续使用冻结参考价对应的原有限价，目标金额仍由服务器按QMT提交时的账户资产计算。QMT先卖后买和续单规则保持原样。这次没有修改完整QMT本地版策略。

使用时同步更新`good_etf.py`和研究根目录的单文件`bullet_trade_jq_remote_helper.py`（API25），按下文导出和冷启动流程操作；私有连接配置与账户开关无需修改。

helper按D021不防御同进程恶意Python代码；旧版远程交易API（`configure`/`install_jq_compat`/`RemoteBrokerClient`/order系列）与全部同进程对抗机制已在L00删除。同一进程内同签名重装幂等返回；签名漂移或检测到上一代helper遗留记录即失败关闭，必须使用干净进程重启，禁止reload或热补丁。

## 直接复制语义

标准工作流是：

1. 参考[`jq_runtime`说明](../../jq_runtime/README.md)，在仓库外的私有文件中维护连接配置。
2. 本目录策略源码保持 `from jqdata import *` 和顶层helper导入；本地和聚宽使用同一个策略文件，
   不维护本地专用分支。
3. 在仓库源码中审查顶部的`VALIDATE_REMOTE_DURING_BACKTEST`、可选`STRATEGY_ID`和`QMT_INITIAL_CAPITAL`；回测自动使用`BACKTEST`。省略ID只运行JQ且不远程预检；显式ID未匹配配置键时仍默认只启用JQ。模拟交易仅按显式ID的同名配置开关选择账户。
4. 使用[`scripts/export_joinquant.py`](../../scripts/export_joinquant.py)执行Python 3.8语法、明显凭据扫描、
   profile形状和私有profile只读门禁，并生成原样文件与确定性manifest；完整步骤见
   [`聚宽校验与导出`](../../docs/live-ledger/06-joinquant-export.md)。单文件bundle不是标准路径。
5. 核对manifest中各文件SHA256与受控源码的部署声明（`VALIDATE_REMOTE_DURING_BACKTEST`/`STRATEGY_ID`），停止旧进程后上传统一helper与已校验的私有
   `jq_runtime_config.py`，最后把导出的策略原样复制到聚宽编辑器。
6. 导出后和聚宽侧均禁止再次编辑部署声明或helper；任何变更都回到受控源码重新校验、导出并冷升级。

更新helper/config/策略时必须冷升级：先停止策略并确认旧进程退出，再替换文件，最后让聚宽启动全新进程并重新完成marker/profile/执行模式校验；禁止在旧进程内reload或热补丁。任何启动失败都应丢弃该进程，修正后再次以全新进程启动。

“代码一致”指同一份策略源码和已验证API契约，不代表本地兼容引擎与聚宽私有撮合实现绝对相同。

本地解释器、PyCharm和严格类型检查的设置见
[`聚宽本地开发与兼容矩阵`](../../docs/live-ledger/05-joinquant-development.md)。类型模型只在
`TYPE_CHECKING`分支加载，不会让上传后的策略依赖BulletTrade服务器包。
